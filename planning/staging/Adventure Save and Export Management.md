# Adventure Save and Export Management

## Idea
Create, autosave, resume, rename, duplicate and delete individual adventures **within one SQLite library**; provide **Backup Database** and **Restore Database** as the only file-based data transfer operations, covering all adventures together.

## Why this idea matters
Long stories need recoverable and portable saves.

## Accepted direction
- **Multiple independent adventures:** A player can create and manage multiple separate saved stories **inside one shared SQLite library database** (IDEA-0051). Adventures have stable separate identities and do not share canonical narrative/world state by default.
- **Autosave, with two distinct persistence states (explicitly accepted):** Autosave **unfinished player input and prose edits as noncanonical drafts** in the same Go-managed SQLite library after a short inactivity pause; restore those drafts when the browser/editor is reopened. Draft saves must **not** create accepted turns, canonical story revisions, world events or expensive history reconstruction. **Committed turns and confirmed story revisions** persist separately and atomically with all validated state/event changes. Do not require a manual Save button for ordinary committed progress.
- **Resume:** Reopen an adventure at its last reliably saved state.
- **Rename:** Change an adventure's display name without altering its contents.
- **Full-history duplication (explicitly accepted):** Duplicating an adventure creates a **new, independent adventure** with its own adventure identity and an exact copy of the **entire committed history up to the duplication point**, not just the latest turn or current world state. Preserve every accepted story turn, versioned prose and revision lineage, event/state change, baseline, entity, lore/knowledge, memory/summary data, relevant nonsecret configuration and persistent plugin/module state necessary to reconstruct/play the duplicate. All copied references and provenance must remain coherent within the new adventure. **Do not copy unfinished player input or unconfirmed prose-edit drafts**, nor provider credentials. Both adventures continue independently after duplication.
- **Database import/restore (revised accepted workflow):** Importing a **whole-library SQLite snapshot** intentionally **replaces the currently active SQLite database**. It does **not** merge an adventure into the existing library. Earlier single-adventure import language has been superseded by IDEA-0051/0052.
- **Full-library backup only:** Backup creates a **consistent SQLite snapshot of the complete shared database**, including every adventure, editable narrative and revisions, event history, world state, lore, memories and persistent plugin state. **Individual-adventure file exports are explicitly excluded**, superseding the earlier scope.
- **Confirmed permanent deletion (explicitly accepted):** After a clear user confirmation, permanently delete **only the selected adventure** and its associated story turns, text revisions, accepted events/world state, entity records, lore/memory, saved drafts, plugin-owned records and other adventure-scoped SQLite data. Perform the related deletes as **one atomic SQLite transaction** so failures cannot leave half-deleted data. **No recycle bin, soft delete, undo window, delayed cleanup or automatic pre-deletion backup** is required; other adventures and the shared database remain intact. A previously created **whole-database snapshot** is the only planned recovery route, and restoring it replaces the entire current library.
- **Credential exclusion:** Never include provider API keys, passwords, authentication tokens or similar secrets in exports.

## Proposed behaviour
Provide an adventure library with Create, Resume, Rename, **full-history Duplicate**, and **permanent Delete after confirmation** for individual adventures. Duplicating at Turn 150 creates another adventure with all 150 committed turns and their supported history, state and plugin data, but **no pending drafts**; neither adventure's later edits affect the other. Deletion removes the selected adventure and all its owned canonical/history/draft/plugin records in one Go/SQLite transaction, leaves unrelated adventures untouched, and does not maintain a trash or recovery system. While a player types input or edits a story passage, the frontend **debounces ordinary SQLite draft writes** through Go after a short pause, restoring persisted drafts on reopen. These **do not alter canon**. On submit or appropriate historical-edit confirmation, the TypeScript coordinator validates the requested gameplay/story change and Go atomically saves the accepted turn/revision and associated canonical event/state changes. Do not treat an incomplete generated response as committed. If generation or commit fails, preserve the previously committed story/world and keep the player's input recoverable for retry. **Backup Database** downloads a consistent SQLite snapshot of **all** adventures; **Restore Database** deliberately **replaces the entire current SQLite database**. These are the only file export/import operations; provider API credentials remain outside the snapshotted database.

## Alternatives and trade-offs
**Whole-library SQLite snapshot is the only accepted data-export format.** In-library **draft autosaving is not a backup/export format or separate database**. Saving each keystroke and making unfinished text canonical immediately are not selected; draft writes are lightweight and debounced, with an exact interval to be chosen during implementation. The earlier proposed single-adventure archive export and standalone plain-text/Markdown export are **outside this approved backup/export workflow**; supporting any new export format would need a separate future decision. No merging, automatic library migration or advanced corruption-repair system is required.

## Architecture integration (2026-10-17)
- All adventures are durably stored in **one Go-managed SQLite database** for **Wails v3 headless localhost Go server delivery only**, with play through the normal browser. The SQLite library defaults to the **OS's per-user app-data directory**, with an **optional custom directory** (IDEA-0051). Browser-owned storage is not the source of truth.
- Draft autosave, committed turn/revision saves, resume, duplication, **whole-database backup** and **whole-database replacement restore** operate through Wails Go persistence services. **Draft records are explicitly marked provisional and kept separate from canonical revision/event history**. Go creates a consistent SQLite snapshot, closes or quiesces database handles for replacement, then reopens the selected DB. The frontend sends typed requests and renders outcomes; Go applies atomic save operations.
- **One active database and simple directory selection:** Under IDEA-0051, Go opens an existing library database in the chosen app-data/custom directory or creates an empty one if absent. It does **not migrate or merge** the old database on directory change. Backup snapshots the **whole active database**, and Restore Database replaces **the whole active database**. **Per-adventure export/import is explicitly out of scope.** Credential exclusion must hold for SQLite snapshots.

## Minimal adventure creation and naming
- IDEA-0006 explicitly permits **new adventures with no player-entered title or opening prose**. Save a newly created blank adventure as an independent record in the existing SQLite library, using **`Untitled Adventure`** when no display name is supplied. Adventure identity is a distinct stable ID, **not** its title; multiple untitled adventures must not collide, merge or overwrite one another.
- A player may rename the adventure later through the existing **Rename** action without affecting its saved history or stable ID. No character creation, setting questionnaire or AI-generation prerequisite is imposed by the save layer.
- Blank creation and title assignment do not constitute a generated or validated world-state event. Once play begins, the existing debounced draft/atomic committed-turn distinction applies.

## Automatic first-turn commit for Quick Start
- When a player chooses **Quick Start**, a **fully generated and validated AI opening is automatically committed as the adventure's first canonical story turn**, along with any accepted initial world-state/events in **one SQLite transaction** (IDEA-0006). **No separate review/Accept click** is required for a successful opening.
- Incomplete, streamed, cancelled, rejected or failed AI output remains provisional and is **not** stored as a canonical turn/state. The player can retry. This **does not** bypass the explicit confirmation gate for subsequent **historical prose editing** (IDEA-0041), nor does it turn ordinary autosaved player input into canon.
- Creating a blank Custom Opening remains valid with no AI call; full-library Backup Database / Restore Database rules remain unchanged.

## Custom Opening and optional pre-turn Lorebook generation
- **Accepted IDEA-0006:** A player-authored Custom Opening may be blank or contain prose. **Only once prose is committed** may enabled structured-world systems extract and save **explicitly supported facts**, coherently with the accepted passage. Unfinished drafts never affect canon or trigger unseen lore creation.
- **Accepted IDEA-0066:** At adventure creation, the player may **optionally request AI to generate the starting Lorebook before any narrative turn exists**. When the content is accepted under its future-refined workflow, store its adventure-scoped persistent lore/entities in the **same shared SQLite library** without fabricating a played Turn 1. This does not change ordinary autosave, full-history duplication, adventure deletion or **whole-database-only** Backup/Restore.
- The world-generation review/commit flow, size, interruption handling and exact schema need a **separate future refinement**, not a presumed implementation.

## Persisting the selected Playing As character
- **Accepted IDEA-0002/0007/0026 selection:** `Playing As` is an **optional per-adventure setting**, pointing by stable ID to an existing Lorebook character. On adventure resume, restore the valid selection, or represent it as unset if absent/invalid; **Do and Say require a valid selection** but **Story and Continue do not**.
- The selector's **Add Character** action navigates to manual Lorebook entry; creating **one or multiple** characters does not fabricate a gameplay turn, transfer inventory, **set or replace the saved `Playing As` selection**, or automatically return the user to the story. Only a deliberate Settings character choice changes the saved selection. Changing selection is a lightweight setting change, not a canonical world-state mutation or an edit of historical actor attribution.
- Selection persistence lives in the same shared SQLite library with other adventure settings and follows the existing complete-library backup, restore and duplication boundaries. Exact selected-ID handling during duplication/deletion is normal referential-integrity design, not a new import/export function.

## Dependencies and constraints
- Depends on the **shared filesystem-backed SQLite database** via Go, with per-user OS app-data default and optional custom directory (IDEA-0051), transaction-safe storage, stable IDs and event/document revision history.
- Duplication **within the same shared SQLite database** must create a **distinct adventure identity**, copy complete accepted canonical story/revision/event/state and relevant lore/plugin history, and preserve coherent **internal source/event/entity/revision references** in the copy. The exact ID-remapping strategy (new identifiers versus correctly scoped existing identifiers) is an implementation choice; never allow copied records to point to mutable source-adventure data inadvertently. **Do not carry over pending noncanonical drafts**. Use a coherent atomic copy operation so a failure does not leave a partially populated duplicate.
- Saving a narrative turn, its accepted story revision and validated state events must be **one atomic committed operation**. An interrupted/failed model request, rejected action or failed commit **must not partially mutate canonical state**; keep the last saved player draft available for retry and show save/failure status. A few characters typed since the last debounce may remain unsaved if the process ends abruptly; do not promise synchronous per-keystroke durability.
- Whole-database SQLite snapshots must not leak provider credentials, passwords or tokens. Store such secrets **outside** the library database included in the snapshot; restoring does not automatically restore third-party secrets.
- Full-fidelity restoration may depend on optional plugins being installed and on compatible schema versions; missing extensions should be handled explicitly.
- Exported model/provider configurations may be informative even if the specified model is not available on another machine; portability does not guarantee model availability.

## Open questions
- What minimal compatible-SQLite-file checks and Go connection close/reopen behaviour should govern **whole-database replacement**, with no ID-collision merge workflow?
- How prominently should the UI explain that **Restore Database replaces every adventure** currently saved, without introducing a merge or selective restore feature?
- What debounce delay, editor focus/blur handling, draft save indicator and conflict/version policy best balance responsiveness and durability? Drafts persist in SQLite, so the last successfully saved draft can be restored after a browser restart; disk-full/write failures must be visible.
- When exactly should a completed/committed turn retire its source draft, and how should failed generation/commit and interrupted submissions retain or restore player input?
- **Resolved:** Deletion is **permanent immediately after confirmation** with **no** trash, retention period, or automatic backup. Which concise confirmation wording and Go/SQLite adventure-scoped deletion API should be used remains a UI/implementation detail.
- What happens when a whole-library restore references providers or plugins unavailable in the current installation? No automatic model/plugin installation is implied.

## Draft acceptance criteria
- [ ] A player can create, name, reopen and resume multiple distinct adventures.
- [ ] A completed turn or explicitly confirmed revision is **atomically committed** with every validated canonical event/state effect; partially generated, invalid or failed turns do not change authoritative story/world state.
- [ ] While typing an input or editing prose, Lorebound writes a **noncanonical draft to the shared SQLite database after a short pause**, without creating a story revision, event, tool side effect or historical state rebuild.
- [ ] Closing and reopening the browser/editor **restores the last successfully autosaved draft** independently of the last committed narrative/world state.
- [ ] Submitting/confirming a change invokes validation and atomic committed persistence; failures leave prior canon unchanged and the player's latest saved input available to retry.
- [ ] Clear draft/save status and ordinary write failures are surfaced; exact debounce interval and unsaved-last-keystrokes behaviour are refined before promotion.
- [ ] Renaming an adventure preserves its story and world-state data.
- [ ] Duplicating an adventure at Turn N creates a **new adventure with its own identity and every committed turn through N**, including prior prose revisions, event/world-state history, canonical entities, lore and persistent plugin data, sufficient for deterministic reconstruction.
- [ ] **No unfinished player input or unconfirmed prose-edit drafts** are copied. The duplicate starts with no pending user draft while preserving the source's accepted story history.
- [ ] Source and duplicate can thereafter be edited/continued independently, without shared mutable records or cross-adventure entity/provenance reference errors. The copy is atomic; a failed duplication cannot leave a partial saved adventure.
- [ ] **Backup Database** captures the **whole SQLite library**, with every adventure and canonical history; **Restore Database** replaces the complete active library. **No individual-adventure export/import** is offered.
- [ ] Importing a compatible whole-library snapshot **replaces the active SQLite database**, with no per-adventure merge, optional automatic backup or separate library-management UI.
- [ ] The library SQLite database contains no provider API keys, passwords or tokens that would be disclosed by copying the **whole database snapshot**.
- [ ] Deleting an adventure requires an **unambiguous player confirmation**; on confirmation, Go/SQLite atomically removes the adventure and **all its adventure-scoped dependent data**, including drafts, revisions/events/world state and plugin records, with **no soft-delete or recycle-bin mechanism**.
- [ ] Deletion never removes other adventures or damages shared SQLite library data. A failed database transaction leaves the adventure intact, not partially deleted.
- [ ] Lorebound does **not** automatically create a backup when deleting. Restoring a previous whole-database backup is possible only by overwriting the **entire** current library, not by selectively restoring the deleted adventure.
