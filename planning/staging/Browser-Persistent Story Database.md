# Browser-Persistent Story Database

## Idea
Choose and refine **one shared filesystem-backed SQLite database for the entire Lorebound adventure library**, accessed through Wails v3/Go services, as canonical persistent storage for the headless localhost server and normal-browser frontend. The earlier browser-only/server/hybrid comparison has been superseded by the user's 2026-10-17 explicit runtime/storage decision. Exact schema, platform-specific path resolution, snapshot implementation, safe database replacement mechanics and performance policies remain for refinement; **automatic directory migration, library management and sophisticated corruption recovery are not required**.

## Why this idea matters
The product must reliably store substantial adventures with many story turns, revisions, entities and complete incremental changes. The selected Wails v3 headless Go localhost service provides one filesystem-backed SQLite database boundary for the normal-browser frontend. The remaining design concerns are ordinary SQLite persistence, durable transactions, consistent history, full-database snapshot/restore and acceptable error handling, not multiple-library management, automatic migration or speculative disaster-recovery systems.

## Accepted direction
- **One SQLite database for the entire library (explicitly chosen):** Use **one shared SQLite database file**, provisionally referred to as `lorebound.db`, for **all adventures** and their associated canonical narrative text, revisions, events, entities, world state and durable plugin records. The filename is illustrative; the **default parent directory is now selected** below, while the final filename and path resolution implementation remain open. Go/Wails owns reads, writes, ordinary schema updates and transactions. Do **not** create one database file per adventure or a separate `library.db` plus adventure databases.
- **One headless runtime:** Wails v3's localhost Go server serves the SvelteKit frontend to the normal browser and exposes Go persistence services. No separate native window/WebView or Node/SvelteKit SSR player server.
- **Logical adventure isolation within the shared database:** Each adventure's story and world history must remain separate through durable identity and appropriately scoped queries, writes, deletes and duplication. **A confirmed adventure deletion atomically and permanently removes that adventure plus all its dependent story, revisions/events, world state, noncanonical drafts and plugin-owned data**, leaving unrelated adventures intact. No application trash/soft-delete scheme or automatic backup is required. Schema/table shapes, referential-integrity constraints and IDs still need detailed design.
- **No browser-owned canonical saves:** Browser localStorage, IndexedDB, SQLite WASM/OPFS and browser quotas are not authoritative adventure storage. UI preferences or disposable caches may be browser-scoped without violating this decision.
- **Atomic history:** A committed turn, versioned prose and accompanying canonical events/state must be durably committed together or not at all. Concurrency control must prevent stale browser tabs or simultaneous clients from overwriting one another.
- **Only two database transfer operations (explicitly accepted):** **Backup Database** creates a transactionally consistent SQLite snapshot of the **entire active database**, containing every adventure. **Restore Database** replaces the **entire active database** with the chosen backup. **No single-adventure export or import, merge, adventure-ID reconciliation, multiple-library management, or alternate playable save-package format** is part of this scope. Do not naively copy a live database in WAL mode. The user explicitly superseded earlier per-adventure export proposals in IDEA-0005/0052.
- **Default data directory (explicitly accepted):** Resolve Lorebound's **per-user OS application-data directory** as the normal location for the single shared SQLite library, **not** the directory containing the executable or an ephemeral working directory. Illustrative default paths: **Windows** `%APPDATA%\\Lorebound\\lorebound.db`; **macOS** `~/Library/Application Support/Lorebound/lorebound.db`; **Linux** `${XDG_DATA_HOME:-~/.local/share}/Lorebound/lorebound.db` (honour `XDG_DATA_HOME` when set). The database filename is provisional and the exact platform-specific resolution code is not yet chosen.
- **Optional user-selected data directory (explicitly accepted):** Allow a **custom directory** for the persistent SQLite library, e.g. a portable installation or alternate drive. Go resolves and accesses this path, subject to filesystem permission and safety checks; the browser must not gain arbitrary filesystem access. **When the configured directory already contains the selected Lorebound SQLite database, open/use it; when it does not, create and initialise a new empty database. Do not automatically copy/migrate/merge/replace a database from the previously configured location.** Only **one active library database per running Lorebound server** is supported; no multi-library browser, catalogue or switching/merge UI is required. The old file, if any, is simply left at its original path.
- **Companion files and minimal safety:** SQLite WAL/journal companion files can reside alongside `lorebound.db`, but they are **not separate adventure databases**. Use SQLite-supported consistent snapshot procedures; an import of a snapshot should close/reopen database access so no stale handles or WAL files corrupt the replacement. No automatic prior-library migration, extra restore copies or sophisticated corruption-recovery feature is promised. Ordinary error reporting and atomic turn commits remain required.
- **Secrets excluded from whole-file backups:** Provider API keys and sensitive credentials must **not be stored in the SQLite library file if it will be distributed verbatim as a backup**; keep them separate or use an explicitly designed exclusion mechanism. A raw SQLite snapshot cannot selectively omit a secret already stored inside it.
- **Go is a persistence boundary, not a parallel game engine:** The coordinator, validators and gameplay plugins remain frontend TypeScript (IDEA-0044/0047/0055). Go validates data/service requests for safety, expected versions and transaction integrity; it must not blindly permit conflicting durable writes.
- **Selected architecture is staging direction only:** This does not assert SQLite tables, a driver, an export file layout or an implemented database already exists.

## Historical storage alternatives (superseded)
**Historical alternatives, superseded by explicit user choice on 2026-10-17:** Browser localStorage, IndexedDB, SQLite WASM/OPFS, SvelteKit server SQLite, hosted PostgreSQL and hybrid sync were considered while the storage direction was undecided. None are now selected as alternate canonical stores for initial Lorebound. They may be reconsidered only through a later explicit decision; the current architecture is **Go/Wails + filesystem SQLite**.

## Proposed behaviour
The player's SvelteKit/Svelte UI and browser-side TypeScript game logic request durable records through Go/Wails service bindings. Go stores adventures and all canonical state/history in a persistent local SQLite database and returns typed data to the frontend. At the configured location, Go opens an existing Lorebound SQLite library database or creates a new, empty one if no database exists. There is **only one active database**; selecting another directory never triggers automatic library relocation, merging or app-maintained alternative-library management. Atomic commits verify the target adventure's expected revision, then persist its accepted text revisions/events/state records in one SQLite transaction. A backup request creates a **transactionally consistent snapshot of the whole database**. Import/restore deliberately **replaces the complete active database** with the selected snapshot and reopens it, rather than merging records into a library. The user does not require additional corruption-repair or automatic migration workflows. Normal operational failures are reported without promising repair.

## Alternatives and trade-offs
- **Selected single-file SQLite/Go:** One SQLite database simplifies indexing, ordinary schema migrations and whole-library backups; it permits atomic multi-table writes. Keep practical database-connection, WAL and concurrent-tab consistency, but **do not build automatic cross-directory migration, multiple-library management or advanced repair** as part of the accepted requirement.
- **Browser IndexedDB/OPFS and hybrid sync:** Not selected for canonical saves. Avoids a headless Go server in browser-only hosting but conflicts with the accepted single filesystem persistence model.
- **Node/SvelteKit server SQL:** Not selected because the headless web entry point is Wails v3's Go HTTP server.
- **Hosted SQL/remote multiplayer:** Not selected; app stays single-user/local-first. Remote server deployment and authentication are separate, unapproved concerns.
- **Rejected per-adventure physical databases:** Separate SQLite files per adventure plus a central `library.db` index are **not selected**. Each adventure remains a logical partition within the one database, not its own `.db` file.
- **Backup/restore scope selected:** All backup/export operations are **full-library SQLite snapshots** and all import/restore operations **replace the entire database**. Earlier per-adventure export/import ideas and optional JSON or Markdown archive transfers are not accepted capabilities in this workflow. A consistent SQLite snapshot avoids incomplete copies of a live WAL database.

## Noncanonical drafts and canonical history
- Within the **one shared Go-managed SQLite database**, keep **debounced player-input/prose-edit draft records separately** from accepted canonical text revisions, turns and world events. They survive browser restart without changing canon.
- Draft autosaving does not trigger validation, historical replay or new accepted event provenance. A confirmed edit or completed validated turn commits canonical prose and all associated state changes together atomically.
- **Only the most recently successfully saved shared draft per logical editing target** is recoverable after browser interruption. Later saves from another tab can replace it intentionally; no older draft-copy history is promised. Exact debounce and draft-target keying remain for implementation.

## Full-history duplication within the shared library
- **Duplicate Adventure** copies one adventure's **entire committed canonical history** (all accepted turns, text revisions/lineage, events, world state, entities, lore, memories and durable gameplay-plugin data) into a **distinct adventure identity** in the same shared SQLite database. Only committed material is copied; **noncanonical player-input and prose-edit drafts are excluded**.
- Ensure coherent internal IDs and references in the duplicate, with no mutable records or dependencies unintentionally shared with its source. Whether scoped IDs can be retained or need remapping is a schema detail, not a new acceptance gate.
- Duplicate as one coherent database operation or transaction, so failures do not create half-copied adventures. Both copies can evolve independently. This is **not** file export/import; the only data-transfer functions remain full SQLite snapshot Backup Database/Restore Database.

## Single-instance ownership of the active SQLite library
- **Explicit IDEA-0053 user acceptance (2026-10-18):** Lorebound's executable uses a **single running headless server instance for its active application/library**. A second executable launch connects to/reopens the first server's browser address instead of creating a second competing Go server against the same SQLite file. This is independent of the already accepted one-file library architecture and does not create a library-manager feature.
- **Distinct processes versus browser clients:** Multiple browser windows/tabs may access **one** server; Go/SQLite must still enforce expected revision checks, transaction boundaries and write conflict handling. Prevent racing **server processes** that believe they exclusively own the same active library, including rapid double launches. The exact OS-level single-instance claim, connection/handoff and stale-owner recovery remain for runtime implementation.
- **Failure boundary:** A crashed/defunct previous process may leave a stale owner marker; startup must recover safely rather than accept two live owners or strand the app. Any port/handshake result must be verified as the intended Lorebound server and must not compromise loopback security. Do not silently switch directories, create a new database or auto-migrate data to work around an active-instance conflict.

## Database lifetime follows the headless server, not tabs
- **Accepted IDEA-0053 lifecycle refinement:** One Go-owned SQLite library stays available through the **persistent single-instance headless server**, even if the last browser tab/window closes. Browser client count is **not** a trigger to shut down the process, replace the database, delete drafts or release the app's single-instance ownership.
- The user can relaunch Lorebound and reconnect to the **same existing server/database**. Normal explicit Quit or OS shutdown will end the process; the server should close SQLite resources gracefully where feasible, retaining the existing transaction, WAL and durable history guarantees. Crash/power-loss recovery relies on SQLite integrity rules, not on assuming all unsaved browser input was flushed.
- Successfully written noncanonical drafts and canonical turns remain durable according to existing rules; closing the browser can abandon in-memory unsaved keystrokes and browser-side AI work. The server does not independently finish such client-side tasks. No automatic extra backup or new physical library is implied.

## Explicit in-app Quit closes the SQLite owner
- **Accepted IDEA-0053 shutdown UX:** The normal-browser **Settings → Quit Lorebound** action initiates shutdown of the **single headless server and its Go-managed SQLite library owner**. Quit is app-wide, not merely a tab close, adventure close or data export. No tray/menu-bar helper or competing server is needed.
- **Durability:** Cleanly finish or reject in-flight writes, safely close database resources and release single-instance ownership as feasible, retaining **all successfully committed canonical turns and autosaved draft writes**. Client-side unfinished AI requests and never-autosaved keystrokes are not promised to survive Quit. This does not create a new automatic backup or change established whole-library backup/restore policies.
- Closing the last browser tab continues to leave the server/library open; relaunch reconnects for access to Settings Quit. Shutdown requests must originate from appropriately authorised app clients, not arbitrary origins or another local process.


## Go persistence is a supporting Lore Engine responsibility
- **Accepted IDEA-0061 rename/scope:** The **Lore Engine** collectively labels Lorebound's **non-UI responsibilities**. Under that conceptual umbrella, **browser-side TypeScript** still owns the deterministic gameplay coordinator/rules, while the **single Wails v3 headless Go server** continues to own privileged filesystem/SQLite persistence, safe transactional commits and library backup/restore. The earlier internal label `Lorebound Backend` is superseded.
- **No split or migration caused by naming:** Go persistence does not become a second gameplay authority or a separately deployed Lore Engine service; the project keeps one server and one active Go-managed SQLite library with existing client revision checks, transaction boundaries and backup/restore policies. The exact code structure remains future design.

## Optimistic multi-tab adventure writes and nonclobbering drafts
- **Accepted IDEA-0005 user decision (2026-10-18):** Multiple browser tabs may open and **edit the same adventure** through the one Wails v3 headless Go service. No mandatory exclusive editor lock or read-only secondary tab. Go/SQLite enforces **optimistic expected-version checks** in its atomic canonical commit transaction: reject a change prepared against an older authoritative adventure state, even if the browser's TypeScript coordinator previously validated it.
- Example: Tabs A and B both read version V. If A commits V+1 first, B's subsequent commit prepared from V is refused as a **stale-version conflict**, with zero partial text revisions, entity, item, Lorebook, state events, memory or plugin-effect writes. B may keep local edits and select an explicit resolution path; the DB must **never silently overwrite** A's accepted work or implicitly auto-merge conflicting histories.
- **Draft-only policy superseded (2026-10-18):** Earlier cross-tab draft-clobber avoidance is **replaced** with user-approved latest-saved-value overwrite for the same logical draft target. Noncanonical draft saves require **no draft-version conflict rejection, per-tab copies or merge history**, but **canonical commits** must still pass expected-version checks. See latest-draft section below.
- **Atomicity and clients:** Version checks and writes must be one transaction so two simultaneous requests cannot both win at the same expected state; source revision provenance remains coherent. Distinguish multiple browser clients of **one** server from forbidden competing Go server processes. This does not change whole-database backup/restore or directory policy.

## One shared latest draft per editing target, separate from canon
- **Explicit accepted IDEA-0005 Option B (2026-10-18):** Autosave **every player-authored noncanonical draft** into a **single replaceable shared slot per logical editing target**, including unsent composer messages and unconfirmed edits to story prose, whether current or historical. Key distinct types/targets separately so an unsent composer message cannot replace a passage-edit draft, and editing one passage cannot replace a different passage's draft.
- **Last successful save wins:** Debounced autosaves from **any tab** can **overwrite the preceding stored draft** for that same target without checking a draft version, locking editors, preserving individual tab histories, showing a draft conflict, or attempting an automatic merge. The user accepts that earlier draft content can be lost. Only the **last successfully applied save** per target is persisted and recoverable, not earlier overwritten drafts. Exact debounce/draft-key mechanics remain open.
- **Noncanonical by construction:** Such replacement **cannot change accepted prose, source revision IDs, events, character/item/world state, or any durable canonical history**. Existing **strict expected-version atomic Go/SQLite guards** continue for all committed operations. A stale tab's attempted committed edit/turn remains rejected and visibly conflicted, regardless of which tab last updated the draft slot.
- **Scope boundary:** In-progress generated AI output is **not automatically included** in player-authored draft autosaving (IDEA-0019). No draft history, cross-tab draft conflict workflow or recoverable overwritten-draft versions are required.

## Template-derived adventures own independent starting records
- **User-accepted IDEA-0008 Option A (2026-10-18):** A reusable template may hold its own definition within Lorebound's accepted local data model, but each new adventure instantiated from it receives **private adventure-scoped copies** of the chosen template Lorebook entities and applicable initial world-state records. Copies may reside in the **same one SQLite library database**, with isolation enforced through new adventure identity, scoping and coherent source/target ID remapping. **No live mutable Lorebook/entity references** may make existing template instances change when the template or a sibling adventure changes.
- **Transaction and provenance:** Save each instantiated adventure with coherent internal character/location/item/relationship references and validated initial state; on rejection or write failure, don't leave a half-instantiated adventure. Preserve the distinction between initial template-derived setup and a previously played adventure's accepted turn/event/revision history; template instantiation is **not** full-history Duplicate Adventure and does not copy noncanonical drafts.
- **No new storage layout:** Separate logical ownership inside SQLite does not imply multiple SQLite files, shared network lore storage, separate adventure exports/imports, or a template-publishing format. Schema details for templates and missing optional modules remain open.

## Fork at any committed turn creates an independent SQLite adventure
- **Accepted IDEA-0011 Option A (2026-10-18):** In the **single Go-managed SQLite library**, create a new logical adventure for a fork from **any committed source turn**. Include coherent canonical baseline/Lorebook, accepted narrative/revision history, ordered events, world state, related entities and applicable persistent data **only through the chosen turn**, including whatever history is required for faithful reconstruction. No named checkpoint or stored snapshot at that exact turn is necessary.
- **Transactional source consistency:** Resolve the chosen committed turn against one consistent source-history version, with the existing expected-version/concurrency protections, and atomically create the independent adventure or fail without stray partial records. Never mix new downstream revisions into an earlier selected prefix because the source changed concurrently. Choose coherent identifier/link remapping or truly immutable infrastructure so **no mutable source/fork record is shared**; exact SQL schema and algorithms remain open.
- **Source and scope isolation:** Forking does **not mutate or truncate** the source's later accepted story/world history; it only excludes those later records from the new adventure. No player drafts, unfinished AI generations or credentials are copied. The operation does **not** require a new database file, per-adventure file export/import, backup/restore, named checkpoint manager or an in-story branch tree. Whole-library backup still includes all adventures, including their forks.

## One canonical head with atomic committed Undo
- **Accepted IDEA-0004 committed Undo Option B (2026-10-18):** Each adventure has **one active accepted story head**, not multiple selectable response variants. A committed Undo transaction moves that head from Turn N to N-1, updates which turn/revision/events are active, and ensures the authoritative world/projections correspond to the surviving committed prefix. It is distinct from disposable latest-draft autosaves and provisional AI retry generation.
- **Atomic concurrency and replay:** The Go/SQLite operation must compare the expected authoritative adventure version, reject a stale rollback without affecting canon, and commit the changed head/event validity and persistent state coherently. Deterministic reconstruction may use valid snapshots but never requires a checkpoint at each turn. Multiple sequential Undos can traverse available committed history to baseline, regardless of the short-lived editing undo stack.
- **No selectable old futures:** After rollback, a new turn may be committed into the **same adventure** without a stored menu of prior Turn N variants. Inactive event/audit data may exist solely for source integrity and must not appear as active alternative continuations or silently affect replay. **Fork** explicitly creates a second adventure to keep both futures independently playable; neither Undo nor Retry implicitly forks.
- **No new storage/export scheme:** All operations occur in the one active library database. Full-history Duplicate copies only the selected adventure's coherent **active committed timeline** and necessary reconstructible state, not an interactive collection of inactive old response candidates. Whole-database backup/restore remains the only file transfer mechanism.

## Dependencies and constraints
- User selected Wails v3 headless localhost only in [[Localhost Startup and Offline Mode]] (IDEA-0053), packaged into Windows/macOS/Linux server executables. The headless mode requires a running Go process but not Node SSR.
- [[Snapshots and Incremental State Rebuild]] (IDEA-0042), [[Event-Sourced World History]] (IDEA-0039) and [[Versioned Text Blocks and Revision IDs]] (IDEA-0040) require full durable reconstructibility at supported history points.
- [[Deterministic Adventure Coordinator]] (IDEA-0044) prepares validated results in browser-side TypeScript, but the Go/SQLite boundary must guarantee transactional, version-consistent writes and reject stale commits; server mode may have multiple tabs/clients.
- [[Adventure Save and Export Management]] (IDEA-0005) and [[Backups Export and Storage Quotas]] (IDEA-0052) remain accepted staging ideas, now **explicitly revised** to require only full-library SQLite snapshot backup and full-library replacement restore. The previous single-adventure portable export/import direction is **superseded by explicit user approval**, not an unresolved candidate.
- No browser-origin storage, external cloud database or inference process is mandatory. Sensitive model API credentials must not enter adventure saves or exports.
- This is staging refinement, not final schema implementation or production approval.

## Open questions
- Which simple setting/launch option selects the OS app-data or custom directory, and how does Go safely close the old database connection before opening/creating the database in the newly chosen directory?
- What SQLite driver, connection pool, WAL, busy timeout, transaction and durability settings suit **one library database** with large adventures and multiple browser tabs?
- What concurrency model or expected-revision token lets Go reject stale writes from multiple tabs/clients without duplicating TypeScript gameplay rules?
- What minimum SQLite schema/version check and error reporting are appropriate on open or replace? Extensive corruption repair, history-preserving restore and automatic migration across directories are not in scope.
- Which SQLite API creates a consistent whole-file backup snapshot, and how does Go replace/reopen the active database safely (including WAL files, open connections and running browser tabs)?
- Which minimal restore confirmation and file checks should precede **intentional full-library replacement** without introducing automatic backup, merging or complex recovery?
- How do database records cover every persistent gameplay plugin field, including disabled/removed plugins, without unreplayable state?
- What benchmarks ensure history replay/queries and large write batches keep the UI responsive?

## Draft acceptance criteria
- [ ] A version-checked, atomic committed Undo moves the active head to the prior committed turn and reconstructs state/provenance without introducing another selectable story timeline or a new SQLite database.
- [ ] A newly committed continuation after Undo uses the same adventure identity with no old variant selectable, and a full-history duplicate reproduces its active accepted timeline coherently.
- [ ] Creating a fork from any committed Turn N produces a complete independent SQLite adventure with replayable accepted state through N, not later source turns, even if no snapshot exists for N.
- [ ] Version-consistent, atomic fork creation prevents half-copied or mixed-source-version data under concurrent source edits, while preserving original history and isolating future writes.
- [ ] Two adventures instantiated from a single template have **independent, correctly scoped initial Lorebook/world records** in the one library SQLite file, with no mutable records linked across template or adventure boundaries.
- [ ] Subsequent template edits and independent gameplay changes cannot silently propagate into other adventures; a failed template instantiation leaves no partially persisted adventure/world records.
- [ ] Unsent composer input and unconfirmed story/history prose edits autosave into **one latest-value SQLite draft slot per logical target**, shared by all tabs, and a subsequent successful save from another tab may replace the prior value without draft conflict checks.
- [ ] Different logical draft targets do not overwrite one another; older overwritten draft versions do **not** require recovery. All such writes leave canonical story/revision/event/world records unchanged.
- [ ] Canonical commits continue to reject stale versions transactionally even where provisional drafts last-write-wins.
- [ ] Two tabs can edit the same adventure. If A commits first, Go/SQLite rejects B's stale expected-version transaction, with **no partial canonical turn, text, events or world data overwrite**.
- [ ] The conflicting tab receives a conflict result and retains its work for explicit user reconciliation; the accepted state remains intact with no implicit merge.
- [ ] Two tab draft-autosaves cannot quietly replace each other's in-progress text. Draft identity/conditional write details are deferred; draft records remain noncanonical.
- [ ] Go/SQLite platform persistence is documented as supporting **Lore Engine** functionality, while the coordinator and gameplay operations remain browser-side TypeScript and no new independent engine/SQL server is required.
- [ ] **Settings → Quit Lorebound** initiates an authorised server/SQLite shutdown and releases resources cleanly without corrupting or partially committing authoritative state.
- [ ] Last-tab closure leaves the shared library available to the running server; all successfully persisted data survives a subsequent explicit Quit/relaunch.
- [ ] The SQLite library remains associated with the single still-running server when all browser clients close; a later browser relaunch reconnects without opening a competing server or separate library.
- [ ] Deliberate server Quit/OS termination releases database handles safely where possible, and only persisted drafts/canonical transactions are promised to survive client closure.
- [ ] A second Lorebound executable launch with an already running server **reuses the active instance**, rather than opening another competing server process connected to its database.
- [ ] Multiple browser clients of the one headless server remain supported with expected-revision and atomic write protections; simultaneous launches cannot create two active owners of the same library.
- [ ] Stale/crashed owner state can be handled safely without starting a second conflicting writer, silently selecting a different SQLite file or locking the user out permanently.
- [ ] The Wails v3 headless localhost server uses filesystem-backed SQLite via Go services and serves the game to normal browsers.
- [ ] No canonical adventure, text revision or world event requires browser localStorage/IndexedDB to survive closing, restarting or switching views.
- [ ] All accepted state mutations and story revisions are persisted durably and are fully reconstructible at supported history boundaries.
- [ ] Go commits a complete accepted turn atomically and rejects stale/conflicting writes; failed writes leave prior canonical state unchanged.
- [ ] **One shared SQLite database file** holds the adventure library; no per-adventure database files or separate library-index database are required.
- [ ] Independent adventures are logically isolated for ordinary operations such as renaming, editing, deleting or duplicating. A confirmed **permanent adventure deletion atomically removes all records belonging to that adventure, including drafts/history/plugin data, without affecting other adventures**, and offers no recycle bin. **Whole-database import** is an intentional exception: it replaces all adventures in the library.
- [ ] **Backup Database** creates a **consistent, complete SQLite snapshot of every adventure** in the active database. **Restore Database** replaces that database **entirely**, without merge or per-adventure export/import.
- [ ] A database backup contains no provider API keys or other credentials that should be excluded from exported game data.
- [ ] By default the library resides in the OS's **per-user application-data location** (Windows `%APPDATA%`, macOS `~/Library/Application Support`, Linux `XDG_DATA_HOME` or `~/.local/share`) rather than beside the executable.
- [ ] At the default or a chosen custom directory, Go **opens the existing Lorebound database if present or creates a new blank database if absent**. The app does not automatically copy/migrate or merge data from any previous location, and offers no multiple-library manager.
- [ ] An ordinary saved database survives normal server restarts and app upgrades; SQLite-supported backup/replace procedures handle relevant WAL/journal state without unnecessary extra recovery features.
- [ ] Whole-library snapshots include the database's complete canonical history and plugin state without model API secrets, and restore replaces the currently active database without replaying external actions.
- [ ] Exact path resolution, simple open-or-create behaviour, connection-safe snapshot/overwrite mechanics, SQLite driver/schema and relevant performance thresholds are resolved before promotion. **No cross-directory migration requirement**.
