# Adventure Save and Export Management

## Idea
Create, autosave, resume, rename, duplicate and delete individual adventures **within one SQLite library**; provide **Backup Database** and **Restore Database** as the only file-based data transfer operations, covering all adventures together.

## Why this idea matters
Long stories need recoverable and portable saves.

## Accepted direction
- **Multiple independent adventures:** A player can create and manage multiple separate saved stories **inside one shared SQLite library database** (IDEA-0051). Adventures have stable separate identities and do not share canonical narrative/world state by default.
- **Autosave, with two distinct persistence states (explicitly accepted):** Autosave **unfinished player input and prose edits as noncanonical drafts** in the same Go-managed SQLite library after a short inactivity pause; restore those drafts when the browser/editor is reopened. Draft saves must **not** create accepted turns, canonical story revisions, world events or expensive history reconstruction. **Committed turns and confirmed story revisions** persist separately and atomically with all validated state/event changes. Do not require a manual Save button for ordinary committed progress.
- **Resume:** Reopen an adventure at its last reliably saved state.
- **Rename:** Change an adventure's display name without altering its contents.
- **Full-history duplication (explicitly accepted):** Duplicating an adventure creates a **new, independent adventure** with its own adventure identity and an exact copy of the **entire committed history up to the duplication point**, not just the latest turn or current world state. Preserve every accepted story turn, versioned prose and revision lineage, event/state change, baseline, entity, lore/knowledge, memory/summary data, relevant nonsecret configuration and persistent plugin/module state necessary to reconstruct/play the duplicate. All copied references and provenance must remain coherent within the new adventure. **Do not copy unfinished player input or unconfirmed prose-edit drafts**, nor provider credentials. Both adventures continue independently after duplication.
- **Database import/restore (revised accepted workflow):** Importing a **whole-library SQLite snapshot** intentionally **replaces the currently active SQLite database**. It does **not** merge an adventure into the existing library. Earlier single-adventure import language has been superseded by IDEA-0051/0052.
- **Full-library backup only:** Backup creates a **consistent SQLite snapshot of the complete shared database**, including every adventure, editable narrative and revisions, event history, world state, lore, memories and persistent plugin state. **Individual-adventure file exports are explicitly excluded**, superseding the earlier scope.
- **Confirmed permanent deletion (explicitly accepted):** After a clear user confirmation, permanently delete **only the selected adventure** and its associated story turns, text revisions, accepted events/world state, entity records, lore/memory, saved drafts, plugin-owned records and other adventure-scoped SQLite data. Perform the related deletes as **one atomic SQLite transaction** so failures cannot leave half-deleted data. **No recycle bin, soft delete, undo window, delayed cleanup or automatic pre-deletion backup** is required; other adventures and the shared database remain intact. A previously created **whole-database snapshot** is the only planned recovery route, and restoring it replaces the entire current library.
- **Credential exclusion:** Never include provider API keys, passwords, authentication tokens or similar secrets in exports.

## Proposed behaviour
Provide an adventure library with Create, Resume, Rename, **full-history Duplicate**, and **permanent Delete after confirmation** for individual adventures. Duplicating at Turn 150 creates another adventure with all 150 committed turns and their supported history, state and plugin data, but **no pending drafts**; neither adventure's later edits affect the other. Deletion removes the selected adventure and all its owned canonical/history/draft/plugin records in one Go/SQLite transaction, leaves unrelated adventures untouched, and does not maintain a trash or recovery system. While a player types input or edits a story passage, the frontend **debounces ordinary SQLite draft writes** through Go after a short pause, restoring persisted drafts on reopen. These **do not alter canon**. On submit or appropriate historical-edit confirmation, the TypeScript coordinator validates the requested gameplay/story change and Go atomically saves the accepted turn/revision and associated canonical event/state changes. Do not treat an incomplete generated response as committed. If generation or commit fails, preserve the previously committed story/world and keep the player's input recoverable for retry. **Backup Database** downloads a consistent SQLite snapshot of **all** adventures; **Restore Database** deliberately **replaces the entire current SQLite database**. These are the only file export/import operations; provider API credentials remain outside the snapshotted database.

## Alternatives and trade-offs
**Whole-library SQLite snapshot is the only accepted data-export format.** In-library **draft autosaving is not a backup/export format or separate database**. Saving each keystroke and making unfinished text canonical immediately are not selected; draft writes are lightweight and debounced, with an exact interval to be chosen during implementation. The earlier proposed single-adventure archive export and standalone plain-text/Markdown export are **outside this approved backup/export workflow**; supporting any new export format would need a separate future decision. No merging, automatic library migration or advanced corruption-repair system is required.

## Architecture integration (2026-10-17)
- All adventures are durably stored in **one Go-managed SQLite database** for **Wails v3 headless localhost Go server delivery only**, with play through the normal browser. The SQLite library defaults to the **OS's per-user app-data directory**, with an **optional custom directory** (IDEA-0051). Browser-owned storage is not the source of truth.
- Draft autosave, committed turn/revision saves, resume, duplication, **whole-database backup** and **whole-database replacement restore** operate through Wails Go persistence services. **Draft records are explicitly marked provisional and kept separate from canonical revision/event history**. Go creates a consistent SQLite snapshot, closes or quiesces database handles for replacement, then reopens the selected DB. The frontend sends typed requests and renders outcomes; Go applies atomic save operations.
- **One active database and simple directory selection:** Under IDEA-0051, Go opens an existing library database in the chosen app-data/custom directory or creates an empty one if absent. It does **not migrate or merge** the old database on directory change. Backup snapshots the **whole active database**, and Restore Database replaces **the whole active database**. **Per-adventure export/import is explicitly out of scope.** Credential exclusion must hold for SQLite snapshots.

## Minimal adventure creation and naming
- IDEA-0006 explicitly permits **new adventures with no player-entered title or opening prose**. Save a newly created blank adventure as an independent record in the existing SQLite library, using **`Untitled Adventure`** when no display name is supplied. Adventure identity is a distinct stable ID, **not** its title; multiple untitled adventures must not collide, merge or overwrite one another.
- A player may rename the adventure later through the existing **Rename** action without affecting its saved history or stable ID. No character creation, setting questionnaire or AI-generation prerequisite is imposed by the save layer.
- Blank creation and title assignment do not constitute a generated or validated world-state event. Once play begins, the existing debounced draft/atomic committed-turn distinction applies.

## Automatic first-turn commit for Quick Start
- When a player chooses **Quick Start**, a **fully generated and validated AI opening is automatically committed as the adventure's first canonical story turn**, along with any accepted initial world-state/events in **one SQLite transaction** (IDEA-0006). **No separate review/Accept click** is required for a successful opening.
- Incomplete, streamed, cancelled, rejected or failed AI output remains provisional and is **not** stored as a canonical turn/state. The player can retry. This **does not** bypass the explicit confirmation gate for subsequent **historical prose editing** (IDEA-0041), nor does it turn ordinary autosaved player input into canon.
- Creating a blank Custom Opening remains valid with no AI call; full-library Backup Database / Restore Database rules remain unchanged.

## Custom Opening and optional pre-turn Lorebook generation
- **Accepted IDEA-0006:** A player-authored Custom Opening may be blank or contain prose. **Only once prose is committed** may enabled structured-world systems extract and save **explicitly supported facts**, coherently with the accepted passage. Unfinished drafts never affect canon or trigger unseen lore creation.
- **Accepted IDEA-0066:** At adventure creation, the player may **optionally request AI to generate the starting Lorebook before any narrative turn exists**. When the content is accepted under its future-refined workflow, store its adventure-scoped persistent lore/entities in the **same shared SQLite library** without fabricating a played Turn 1. This does not change ordinary autosave, full-history duplication, adventure deletion or **whole-database-only** Backup/Restore.
- The world-generation review/commit flow, size, interruption handling and exact schema need a **separate future refinement**, not a presumed implementation.

## Persisting the selected Playing As character
- **Accepted IDEA-0002/0007/0026 selection:** `Playing As` is an **optional per-adventure setting**, pointing by stable ID to an existing Lorebook character. On adventure resume, restore the valid selection, or represent it as unset if absent/invalid; **Do and Say require a valid selection** but **Story and Continue do not**.
- The selector's **Add Character** action navigates to manual Lorebook entry; creating **one or multiple** characters does not fabricate a gameplay turn, transfer inventory, **set or replace the saved `Playing As` selection**, or automatically return the user to the story. Only a deliberate Settings character choice changes the saved selection. Changing selection is a lightweight setting change, not a canonical world-state mutation or an edit of historical actor attribution.
- Selection persistence lives in the same shared SQLite library with other adventure settings and follows the existing complete-library backup, restore and duplication boundaries. Exact selected-ID handling during duplication/deletion is normal referential-integrity design, not a new import/export function.

## Unclassified character selection persistence
- **Accepted IDEA-0026 refinement:** Persist `Playing As` as a nullable reference to **any valid character ID in this adventure's Lorebook**, with **no PC/NPC, Playable or protagonist classification**. Selecting a character is a setting change for upcoming Do/Say input; it does not modify the entity, story, item ownership or existing event history.
- Every newly created Lorebook character becomes an available option but is never auto-selected. Invalid/deleted references leave Do/Say disabled, while Story/Continue stay enabled. Existing backup/restore/duplication policies remain unchanged.

## Playing As changes are not gameplay turns
- **Accepted scene-cut selection (IDEA-0002/0026/0034):** `Playing As` is a per-adventure, nullable **selection setting**. Switching from a character in one location to another elsewhere saves the new selected stable character ID but **creates no canonical turn, world event, movement, inventory transfer or elapsed-time event**. No confirmation or travel narration is required merely to switch.
- The **next Do/Say** retrieves the newly selected actor's actual established location and circumstances. Story/Continue remain independent. The world-state and story revision history of every character are unchanged until an **actual separately validated and committed narrative/action event** occurs.
- Existing setting persistence, backup/restore, character deletion/reference integrity and manual-selection rules stay in place.

## Playing As selection does not create a turn
- **Accepted:** Changing `Playing As` is an adventure setting update, not a canonical story turn, travel event, inventory transfer, movement, time advancement or history edit. The next Do/Say follows the newly selected character at their established location, even when far from the previously selected one. Real events still validate normally, and Story/Continue stay independent.

## Info/Settings panel and noncanonical presentation
- **Accepted IDEA-0062 UI refinement:** The adventure has a shared **Info** and **Settings** tabbed information panel. **Settings** contains the persisted, nullable `Playing As` selection. **Info** reflects the expressly chosen character's existing inventory, tracked status and known location from authoritative records when available; a change of selection changes presentation/context only, not canonical story or world data.
- An adjacent **Lorebook icon immediately to the left of the story input field** opens Lorebook directly; this does not import/export files, create a turn, change draft-save semantics or automatically select characters. The exact layout preferences and Lorebook opening surface remain unselected.

## Multi-tab version conflicts without editor lockout
- **Explicit accepted Option A (2026-10-18):** Two or more browser tabs may open, read and **edit the same adventure** through the one headless Go server. No tab acquires an exclusive adventure-wide editing lease or renders all other tabs read-only merely because it is open.
- **Expected-version check for canonical commits:** Every turn, confirmed story revision/historical edit or other canonical adventure mutation from a tab must identify the authoritative adventure state/version it was based on. **Go/SQLite checks that expected version against the currently committed state within the same atomic write boundary** before accepting the operation. If Tab A commits first and Tab B submits work based on the now-outdated version, **reject B's stale commit without overwriting or silently merging A's changes**. This applies even if B's local TypeScript coordinator validated its proposal earlier; before committing it must be consistent with current authoritative state.
- **Visible conflict and recoverable work:** The stale tab is told that the adventure changed elsewhere, and its **unsaved/unsubmitted edits and player input must remain available** so the player can inspect newer state and decide what to do. Provide an explicit reconciliation path (e.g. refresh/reload canonical history, review differences, copy/reapply/retry the local work) rather than deleting local work, auto-discarding, silently rebasing gameplay events or committing an older world snapshot. Exact UX/merge controls are still a separate design refinement; no compulsory AI-driven merge is selected.
- **Superseded draft restriction (2026-10-18):** The earlier draft-only no-clobber restriction is **replaced** by the newer explicit user decision below. This requirement continues to apply **only to canonical commits**; draft autosaves are deliberately last-successful-write-wins.
- **History, atomicity and scope:** Conflict rejection never partially writes narrative text, world events, entity data, memories or plugin effects; source revision IDs and committed history remain intact. The chosen rule coexists with multiple tabs of **one server process** (IDEA-0053), one SQLite library (IDEA-0051), and the existing historical-edit confirmation (IDEA-0041). This is **optimistic concurrency**, not mandatory read-only secondary tabs or a server-side lock held during editing.

## Latest-draft-wins for every noncanonical player draft
- **User explicitly accepted Option B (2026-10-18), refining the previous Option A:** Keep **one saved draft per logical editing target**, shared across browser tabs. **All player-authored, noncanonical drafts** use this simple policy: unfinished/unsent Do, Say, Story or other composer input; unconfirmed edits to current story prose; and unconfirmed historical prose edits. These are **distinct logical targets**, not one global text slot that allows an unsent action to replace an edit to a particular passage.
- **Clean overwrite:** A successfully applied debounced autosave from **any tab** may **replace the previous stored content of that same draft target**, without a cross-tab merge, draft history, per-tab draft copies, edit lock, stale-draft version rejection or conflict popup. **Last successfully applied autosave wins** for the shared draft target, even if another tab supplied the earlier version. The player explicitly accepts that previous draft text may be lost; do not promise recovery of overwritten drafts. Exact keying by adventure, composer/edit target and source block remains implementation detail.
- **Reopening:** Loading that target restores **only its most recently successfully persisted draft**, not every previously typed or independently tab-local version. In-progress browser memory may still contain other text while a tab remains open, but there is **no persistence guarantee** after it is overwritten or that tab closes. Neither an autosave nor replacement of a draft authorises a story turn or world-state event.
- **Hard canonical boundary:** The relaxed overwrite rule applies **only to provisional player-authored drafts**. It must **never** overwrite committed narrative prose, accepted text/revision history, gameplay events, world state, Lorebook canon or plugin effects. The separately accepted **expected-version, atomic conflict rejection** is mandatory for every canonical commit. If another tab has advanced the authoritative adventure, submitting an older draft can be **rejected as stale**, notwithstanding that drafts were freely overwritten. Make this conflict visible and allow reconciliation of any input still available locally or in the latest shared draft, without falsely guaranteeing all replaced text survives.
- **Scope clarification:** Provisional streamed/generated **AI output is not automatically part of this player-authored autosave system** (IDEA-0019). Exact draft debounce, replacement ordering, draft removal on successful commit and failure indicators remain refinement questions; no durable draft-version archive or cross-tab reconciliation engine is required.

## Quick Start failure does not create a fallback adventure
- **Accepted IDEA-0006 Option A (2026-10-18):** For a new adventure created via **Quick Start**, an opening request that fails, is cancelled, is invalid, has no configured usable model or returns only partial AI output **keeps the player on the Quick Start setup screen with the premise intact**. The UI offers Retry and an intentional switch to Custom Opening; **do not automatically create a saved blank adventure** or commit a first turn/state because the requested AI opening failed.
- **Successful first-turn transaction unchanged:** On full successful generation and validation, accept the new adventure/first-turn opening and supported grounded initial world facts together through the Go-managed SQLite transaction, without an additional approval click. A failed attempt cannot create a half-initialised canonical Quick Start adventure. The exact pre-commit provisional identity/schema handling remains an implementation choice; it must not leave a mistaken blank fallback entry in the library.
- **Explicit blank creation remains valid:** A player choosing **Custom Opening** may create a fully blank saved adventure as previously accepted, even without AI. Preserve a user-created adventure or separately accepted pre-Turn-1 Lorebook content if the player explicitly established it before a later opening request; do not delete established data on AI failure. Switching from Quick Start does not itself commit the retained premise as story text.
- **Setup premise is not yet a canonical draft:** Keep it available in the setup UI after failure; this decision does not add compulsory SQLite autosave or draft history for the premise and does not relax the established player-authored draft/latest-value policy for existing adventures.

## Scenario template creation yields independently saved adventures
- **Accepted IDEA-0008 Option A (2026-10-18):** Creating an adventure from a reusable scenario template instantiates a **new adventure identity** and **private copies of template-owned starting Lorebook/world records**, including compatible characters, locations, items, relationships and other valid starting state. Remap or scope entity references coherently within that new adventure; do **not** link mutable records back to the template or any sibling adventure generated from it.
- **Lifecycle independence:** Renaming, editing or deleting the original template must not retroactively alter an already created adventure. Likewise, editing/deleting/playing one instantiated adventure never modifies the template or another instantiated adventure. Instantiation starts at the chosen setup state with **no played turns or historical revisions copied from a pre-existing adventure**, unlike the separately accepted full-history **Duplicate Adventure** operation. Provisional drafts do not carry over.
- **Safe creation:** Go/SQLite must store the new adventure and compatible starting records coherently and validate any structured initial state; a failed instantiation cannot expose a half-created adventure or partially linked entities. Exact schema/ID mapping and unavailable-plugin handling remain for design. This is in-library adventure creation, not per-adventure file import/export or an extra database.

## Manual fork copies accepted adventure history only through a chosen turn
- **Accepted IDEA-0011 Option A (2026-10-18):** Unlike **Duplicate Adventure**, which copies the **entire currently committed adventure history**, a manual **Fork Story** can choose **any committed turn** and creates a **new independently saved adventure** with complete accepted baseline/Lorebook, versioned narrative/history, world events/state, entities/relationships, relevant context/memory and durable plugin data **through that turn only**. Later source turns and their effects are not included in the fork. A named save point or materialised snapshot at the chosen turn is not required.
- **Independent canonical ownership:** Give the fork its own adventure ID and correct scoped event, entity, text and reference relationships; no mutable canonical record is shared with the source. The original and any other forks remain unaffected by subsequent changes or deletion of this fork. Ignore unsubmitted input, unconfirmed prose drafts, incomplete AI output, unfinished operations and provider secrets.
- **Coherent persisted copy:** Validate a genuinely committed turn against a consistent source version and build/commit the new adventure atomically in the existing single Go-managed SQLite library. A failure or concurrent source update cannot leave a partly copied or mixed-revision fork. The exact UI entry point/turn selection, stable-ID mapping and origin metadata are future implementation details.
- **Distinguish from templates and exports:** A template instantiation copies **starting scenario content only** (IDEA-0008); Duplicate Adventure copies **all committed existing history** (IDEA-0005); a fork copies **the full accepted prefix to an arbitrary committed turn** (IDEA-0011). These are in-library operations, not single-adventure file exports/imports or in-chat branch trees.

## Single-head committed Undo and replace-only AI retry
- **Accepted IDEA-0004 clarification and Option B (2026-10-18):** Each adventure maintains **one active canonical narrative head**. Retrying an **uncommitted** AI continuation **replaces/discards the prior provisional candidate** rather than retaining selectable alternatives. When a continuation is committed, only its accepted passage/turn and associated validated state become canon. Successful Quick Start initial openings still commit automatically as separately accepted. This does **not** alter the latest-only shared player-written draft policy or add a permanent AI-output autosave archive.
- **Repeatable committed Undo:** Undo of active Turn N is a **canonical expected-version-checked, atomic Go/SQLite operation** that makes the active head **Turn N-1** and deterministically restores the matching authoritative entity, event, Lorebook/world, derived state and supported plugin projections. Repeated Undo may traverse **all available committed turns**, with the initial baseline as the natural limit, independent of the finite temporary-editor undo stack. A user may then add a **new Turn N in this same adventure**, replacing the discarded active future, with no selectable alternative/old committed continuation left in the editor.
- **Fork to keep both futures:** A separately saved **Fork Story** at a committed point (IDEA-0011) preserves an independently playable alternate future; **Fork is not required merely to continue differently after Undo**. The full-history **Duplicate** operation remains distinct, as do templates and whole-database backup/restore.
- **Event-sourced durability:** Undo does not require naive physical deletion of append-only journal history if inactive provenance is needed for safe replay/audit, but prior undone turns/events must not remain **active or selectable as another version**. Internal audit artifacts provide no restoration promise. Reject stale Undo commits atomically across tabs; do not rewrite later prose or keep stale derived cache state. Exact UX, audit retention and any safeguard for bulk undo remain open.

## Dependencies and constraints
- Depends on the **shared filesystem-backed SQLite database** via Go, with per-user OS app-data default and optional custom directory (IDEA-0051), transaction-safe storage, stable IDs and event/document revision history.
- Duplication **within the same shared SQLite database** must create a **distinct adventure identity**, copy complete accepted canonical story/revision/event/state and relevant lore/plugin history, and preserve coherent **internal source/event/entity/revision references** in the copy. The exact ID-remapping strategy (new identifiers versus correctly scoped existing identifiers) is an implementation choice; never allow copied records to point to mutable source-adventure data inadvertently. **Do not carry over pending noncanonical drafts**. Use a coherent atomic copy operation so a failure does not leave a partially populated duplicate.
- Saving a narrative turn, its accepted story revision and validated state events must be **one atomic committed operation**. An interrupted/failed model request, rejected action or failed commit **must not partially mutate canonical state**; keep the last saved player draft available for retry and show save/failure status. A few characters typed since the last debounce may remain unsaved if the process ends abruptly; do not promise synchronous per-keystroke durability.
- Whole-database SQLite snapshots must not leak provider credentials, passwords or tokens. Store such secrets **outside** the library database included in the snapshot; restoring does not automatically restore third-party secrets.
- Full-fidelity restoration may depend on optional plugins being installed and on compatible schema versions; missing extensions should be handled explicitly.
- Exported model/provider configurations may be informative even if the specified model is not available on another machine; portability does not guarantee model availability.

## Open questions
- What minimal compatible-SQLite-file checks and Go connection close/reopen behaviour should govern **whole-database replacement**, with no ID-collision merge workflow?
- How prominently should the UI explain that **Restore Database replaces every adventure** currently saved, without introducing a merge or selective restore feature?
- **Canonical multi-tab policy resolved:** Use expected-version optimistic concurrency for **canonical commits**, not exclusive editor locks. For **drafts**, use one replaceable saved draft per logical editing target. What short debounce interval, editor focus/blur handling, draft save indicator, stale-canonical-work reconciliation UX, and draft-retirement behaviour on successful commit are needed? The **latest successfully stored draft per target**, not earlier overwritten drafts, is recoverable; disk-full/write failures must be visible.
- When exactly should a completed/committed turn retire its source draft, and how should failed generation/commit and interrupted submissions retain or restore player input?
- **Resolved:** Deletion is **permanent immediately after confirmation** with **no** trash, retention period, or automatic backup. Which concise confirmation wording and Go/SQLite adventure-scoped deletion API should be used remains a UI/implementation detail.
- What happens when a whole-library restore references providers or plugins unavailable in the current installation? No automatic model/plugin installation is implied.

## Draft acceptance criteria
- [ ] Committed Undo of Turn N atomically changes the active head to N-1 and reconstructs all affected world/memory/plugin state without a stale tab overwriting a newer version.
- [ ] After Undo, a new committed turn can extend the same adventure from N-1, with no player-selectable alternate Turn N left in that adventure; a separate explicit Fork is used only when preserving two futures.
- [ ] Retry overwrites only an **uncommitted generated candidate** (no old AI candidate gallery or player-readable variant history); finite temporary editing Undo and deterministic committed Undo are independent.
- [ ] Forking at an arbitrary committed Turn N saves a separately listed new adventure containing **all accepted history and state through N and none after N**, independent of the original. No named checkpoint is required.
- [ ] Source and fork can evolve and be deleted independently; uncommitted drafts, pending generation output and provider credentials are excluded; failed fork creation leaves no half-copied adventure.
- [ ] Duplicate Adventure continues to mean copying the **entire** committed history and scenario instantiation still copies only the selected starting setup.
- [ ] Two uses of one scenario template create two separately identified adventures with **independent template-derived starting lore/world entities** and correct private references; editing either or the template does not alter the others.
- [ ] Template instantiation never clones another adventure's past played turns, player draft input or revision history; a failed initial-state validation/transaction does not leave a partially created independent adventure.
- [ ] A failed or cancelled new Quick Start attempt does **not add an unrequested empty adventure**, first turn or provisional world-state record to the library. It leaves the premise usable on the Quick Start screen for Retry or an explicit Custom Opening switch.
- [ ] A fully validated successful Quick Start creates/commits an adventure and first story turn with validated associated state coherently, with no separate Accept step.
- [ ] Explicit Custom Opening blank creation continues to work without AI, and any prior intentionally committed pre-Turn-1 lore/adventure data survives unrelated later generation errors.
- [ ] Unsent composer input and unconfirmed edits to specific narrative passages each use **a latest-only shared noncanonical draft slot per logical editing target**; a newly applied autosave from another tab can replace its predecessor cleanly without draft-version conflicts.
- [ ] On reopening an editing target, only the last successfully persisted draft is recoverable; overwritten drafts are not promised to be restorable, and a save for a different target does not replace this one.
- [ ] Despite free overwriting of drafts, an older tab's attempted **canonical commit** against stale adventure history is rejected atomically, preserving accepted prose, revisions and world state.
- [ ] Two tabs can view and edit the **same adventure** concurrently; neither must become read-only just because another tab is editing.
- [ ] Given Tab A and Tab B both started from version V, after A atomically commits V→V+1, B's attempted commit based on V is **rejected as stale** even if previously validated locally; A's text, accepted events and world state are not overwritten or duplicated.
- [ ] Tab B receives a clear conflict explanation and can still retrieve/retain its own uncommitted text or input while choosing how to reconcile against current canon; no auto-merge or forced loss of local work.
- [ ] Two tabs autosaving **the same logical draft target** can replace that draft with the **last successfully applied save** without a draft conflict gate or preservation of overwritten versions; distinct targets such as an adventure composer versus a historical prose passage do not overwrite each other. Draft saves never become canonical commits.
- [ ] Canonical writes and their associated event/state/provenance updates are all-or-nothing, including if a stale or competing commit arrives concurrently.
- [ ] A `Playing As` switch persists the selected character identity but does not create a story turn, relocate any character, alter inventory/status or rewrite established history. The subsequent Do/Say uses that actor's saved location context.- [ ] A player can create, name, reopen and resume multiple distinct adventures.
- [ ] A completed turn or explicitly confirmed revision is **atomically committed** with every validated canonical event/state effect; partially generated, invalid or failed turns do not change authoritative story/world state.
- [ ] While typing an input or editing prose, Lorebound writes a **noncanonical draft to the shared SQLite database after a short pause**, without creating a story revision, event, tool side effect or historical state rebuild.
- [ ] Closing and reopening the browser/editor **restores the last successfully autosaved draft** independently of the last committed narrative/world state.
- [ ] Submitting/confirming a change invokes validation and atomic committed persistence; failures leave prior canon unchanged and the player's latest saved input available to retry.
- [ ] Clear draft/save status and ordinary write failures are surfaced; exact debounce interval and unsaved-last-keystrokes behaviour are refined before promotion.
- [ ] Renaming an adventure preserves its story and world-state data.
- [ ] Duplicating an adventure at Turn N creates a **new adventure with its own identity and every committed turn through N**, including prior prose revisions, event/world-state history, canonical entities, lore and persistent plugin data, sufficient for deterministic reconstruction.
- [ ] **No unfinished player input or unconfirmed prose-edit drafts** are copied. The duplicate starts with no pending user draft while preserving the source's accepted story history.
- [ ] Source and duplicate can thereafter be edited/continued independently, without shared mutable records or cross-adventure entity/provenance reference errors. The copy is atomic; a failed duplication cannot leave a partial saved adventure.
- [ ] **Backup Database** captures the **whole SQLite library**, with every adventure and canonical history; **Restore Database** replaces the complete active library. **No individual-adventure export/import** is offered.
- [ ] Importing a compatible whole-library snapshot **replaces the active SQLite database**, with no per-adventure merge, optional automatic backup or separate library-management UI.
- [ ] The library SQLite database contains no provider API keys, passwords or tokens that would be disclosed by copying the **whole database snapshot**.
- [ ] Deleting an adventure requires an **unambiguous player confirmation**; on confirmation, Go/SQLite atomically removes the adventure and **all its adventure-scoped dependent data**, including drafts, revisions/events/world state and plugin records, with **no soft-delete or recycle-bin mechanism**.
- [ ] Deletion never removes other adventures or damages shared SQLite library data. A failed database transaction leaves the adventure intact, not partially deleted.
- [ ] Lorebound does **not** automatically create a backup when deleting. Restoring a previous whole-database backup is possible only by overwriting the **entire** current library, not by selectively restoring the deleted adventure.
